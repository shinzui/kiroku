# shibuya-kiroku-adapter 0.7 → 0.8.0.0: link-only trace correlation on shibuya-core 0.13

## Precondition

The project resolves `shibuya-kiroku-adapter` 0.7.x. Use `rg` to find direct use:
`KirokuAdapterConfig`, `KirokuConsumerGroupConfig`, `kirokuAdapter`,
`kirokuProcessor` and `kirokuConsumerGroupProcessors`. Also look for Shibuya
`Adapter` values the project builds itself, including test fakes.

Then look for anything that depends on processing-span names or trace shape:

- test assertions on span names, trace IDs or parent span IDs;
- dashboards, alert rules, sampling rules or saved searches checked into the
  repository.

If none of these exist, report the edge not applicable and succeed.

This edge has no database half. The adapter adds no migration, and
`kiroku-store` stays on `^>=0.13.0.0`, so no `kiroku-upgrade` edge is entailed.

## Source adaptation

1. **Configuration records gain a strict `telemetry :: AdapterTelemetry` field.**
   `KirokuAdapterConfig` and `KirokuConsumerGroupConfig` both have it.
   - Values built with `defaultKirokuAdapterConfig` or
     `defaultConsumerGroupConfig` need no change.
   - Full record literals must set the field. Prefer rewriting them to start from
     the default function, which is how the adapter documents adding fields.
   - The package uses `DuplicateRecordFields`, and `telemetry` is also a field of
     Shibuya's `Adapter`. Because of that, a bare update such as
     `cfg {telemetry = …}` may be ambiguous. Use the project's existing style for
     other shared fields, such as `batchSize`: generic-lens
     (`cfg & #telemetry .~ …`), `OverloadedRecordDot`, or a type annotation.
2. **Shibuya's `Adapter` gains a strict `telemetry` field.** Every `Adapter { … }`
   the project builds itself must set it, including fakes in tests and
   benchmarks. `AdapterTelemetry`'s constructor is hidden, so start from
   `defaultAdapterTelemetry` and change it by record update. For an adapter the
   project owns, pick a policy as described in the next section and expose it in
   that adapter's own configuration.
3. **New exports.** `Shibuya.Adapter.Kiroku` now re-exports
   `AdapterTelemetry (traceCorrelation)`, `defaultAdapterTelemetry`,
   `TraceCorrelation (..)` and `kirokuDefaultTelemetry`. These are the same
   entities `Shibuya.Adapter` exports, so importing them from both does not
   conflict. A local definition with one of these names might need an import
   hiding.

## Trace shape: decide and report

The new default is `kirokuDefaultTelemetry`, which sets `traceCorrelation` to
`LinkOnly`:

- When an event's metadata carries a W3C `traceparent`, written for example by
  `kiroku-otel`'s `injectTraceContext` on append, its processing span becomes the
  **root of a new trace** with a link to the appending span.
- Under 0.7 the processing span was a child of the appending span, in the
  writer's trace.
- Events without a usable `traceparent` behave as before: they keep the ambient
  parent and get no link.
- A consumer group applies its one value to every member.

`LinkOnly` is the right default for an event store. Subscriptions replay history,
catch up in bulk, and several subscriptions read the same event, so parenting
attaches every subscriber's work to the writer's trace with no time limit.
`telemetry = defaultAdapterTelemetry` (`ParentAndLink`) restores the old shape and
adds the link.

Keep the default unless this project has a concrete reason not to. A concrete
reason would be tests or documented operational practice that need processing
to share the writer's trace. If tests assert the old parent-child shape:

- where the shape was incidental, update the assertion to check for the link;
- where it is a documented requirement, set `ParentAndLink`.

Report which you did and why.

`kiroku-otel`'s own subscription spans do not change. They were always separate
roots, correlated with Shibuya's processing spans by matching `kiroku.*`
attributes. An older adapter changelog note described them as part of one trace,
and that note was wrong.

## Span names and attributes (shibuya-core 0.13)

- Processing spans are renamed from `<processor> process` to
  `process <processor>`.
- They gain `messaging.operation.name = "process"`.
- Lifecycle span names do not change.
- Batch processing spans are now always roots. They link each member event whose
  trace headers decode, up to 128 links, and count any extra links in
  `shibuya.batch.links.dropped`.

Update test assertions, and any checked-in dashboards, alert rules, sampling rules
and saved searches, that match the old names or expect batch spans to join a
member's trace. List the external observability configuration this project
references but you could not edit, so its owners can update it.
