# kiroku-store 0.12.0.0 → 0.13.0.0: selective event compaction

## Precondition

The consumer resolves Store 0.13.0.0 from the 0.12 family. Inspect its source,
framework-owned migrations and persistent database ownership. If no exhaustive
Kiroku matches, affected migration fixtures or owned database apply, report this
edge inapplicable and succeed. Find dependency sources through Mori; the owner is
mori://shinzui/kiroku. Adopting destructive compaction is optional.

Resolve `kiroku-store ^>=0.13.0.0` and `kiroku-store-migrations ^>=0.7.3.0`.
Where consumed, align `kiroku-cli ^>=0.3.0.0`, `kiroku-otel ^>=0.3.0.1`,
`kiroku-metrics ^>=0.4.0.1` and `shibuya-kiroku-adapter ^>=0.7.0.1`.

## Source adaptation

`Store` gains `GetStoreIdentity`, `LookupEventReferences`, `PreviewCompaction`,
`ApplyCompaction` and `GetCompactionLedger`. Exhaustive custom interpreters must
provide those behaviors. `StoreError` gains `CompactionConcurrentMutation digest
guard`; an apply transaction with this error rolled back and needs a fresh preview
before retry. Direct `applyCompactionTx` composition can also receive the existing
`UnexpectedServerError` with SQLSTATE `23503` for a concurrent reference.

`KirokuEvent` gains `KirokuEventCompactionPreviewed`, `KirokuEventCompactionRefused`,
`KirokuEventCompactionApplied` and `KirokuEventCompactionAlreadyApplied`. Add explicit
arms to exhaustive observers, choosing whether to record an audit signal. The
published telemetry/HTTP schemas are unchanged. These signals exclude payloads;
the append-only database ledger and consumer archive provide durable evidence.

`KirokuCommand` gains `KirokuCompaction` and `KirokuStore`. Hosts matching the tree
must handle these or delegate to `executeKirokuCommandWithStore`, which returns
text and an exit code: 0 success/already applied, 2 refusal, 1 file/usage/store
failure. Hosts using `kirokuSubparser` directly inherit the tree. The standalone
remote client refuses these commands; it owns no store and no HTTP apply endpoint
is added. Apply requires a reviewed manifest digest before database access.

New public records use unprefixed labels, including `storeIdentity`, `operation`,
`eventId` and `manifestDigest`. Prefer qualified imports, record patterns or
`OverloadedRecordDot`/generic-lens where selectors become ambiguous; compaction
types use `NoFieldSelectors`. Do not rewrite unrelated records automatically.

## Database cutover

Classify the database read-only, back up and rehearse on a disposable restored
clone. An operator applies migration `0017` through the consumer's existing runner
before enabling the new APIs. Directly owned databases use `kiroku-store-migrate
up`; framework consumers use their composed runner. Do not automatically migrate
persistent data, rewrite checksums, or drop a database.

The native manifest grows from sixteen to seventeen entries. Existing native
stores gain one pending step. Update count, pending-ID and `drop N` fixtures only
where their intended baseline changes. The schema comment becomes `Managed by
pg-migrate component kiroku through 0017`. The new `store_identity` singleton and
`event_compactions` ledger are immutable/append-only; a restored clone retains its
source identity, allowing a reviewed manifest to be rehearsed there.

Existing applications need no new destructive privilege. A separately authorized
maintenance role needs SELECT on identity, ledger, reference and lease inventory,
UPDATE on coordinator/locked streams, DELETE on events/memberships, INSERT on the
ledger and optionally DELETE on dead letters. Do not grant UPDATE/DELETE/TRUNCATE
on identity or ledger. The session hard-delete setting guards accidents; grants
and host authorization control access.

## Optional compaction adoption and validation

The consumer proves redundancy and archives envelopes. Build manifests from exact
identity, memberships and stream-head witnesses; preview read-only, review both
digests and apply with confirmation. Kiroku refuses discrepancies rather than
widening deletion. Active replay-history leases refuse apply; ordered stream
locks follow the retention coordinator. Reapply returns the original ledger row.
Retained versions, stream heads and append frontiers are unchanged; reads and
subscriptions skip gaps. Causation refusal is validation-time best-effort.

Start with 10,000 selections by stream and measure coordinator hold inside lease
renewal margins. The 100,000-selection ceiling does not bound link fan-out or
ledger size. Plan PostgreSQL VACUUM/rewrite work separately for space reclamation.
Read `docs/user/compaction.md` within mori://shinzui/kiroku (artifact-level URI
pending) for the full reviewed workflow, refusal recovery, consumer consequences
and storage operations.

Build and test the consumer with exhaustive-pattern checking. Rehearse migration
on a disposable clone, verify its identity and append/read behavior, and exercise
preview/apply/reapply only if adopting compaction. Report selected versions, source
changes, evidence and any operator work remaining.
