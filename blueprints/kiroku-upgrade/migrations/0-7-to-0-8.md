# kiroku-store 0.7.0.1 → 0.8.0.0

This edge covers two released packages:

- **`kiroku-store` 0.8.0.0** — one new `StoreError` constructor.
- **`kiroku-store-migrations` 0.4.0.0** — a corrected migration payload, which
  changes a checksum an already-migrated database has recorded.
  `kiroku-store-migrations` 0.3.2.0 and 0.3.2.1 are **deprecated on Hackage**.

The two halves are independent. Work through both; each has its own
precondition.

## Precondition

Report this edge **not applicable** only when *both* halves are inapplicable:
the project has no Haskell source that names `StoreError` or its constructors
(directly or through a re-export), **and** it has no PostgreSQL database that
has applied Kiroku migrations. A project that reached this edge through another
library's blueprint and only uses that library's own API — never Kiroku's error
type — but does run a composed migration plan against a persistent database
still needs Part B.

If exactly one half applies, do that half and say so in your summary. That is a
completed edge, not a partial one.

## Part A — `StoreError` gains `TransientTransactionFailure`

### What changed

`Kiroku.Store.Error.StoreError` gains one constructor:

```haskell
TransientTransactionFailure !Text !Text
--                           ^ SQLSTATE code
--                                 ^ human-readable message
```

PostgreSQL's class-40 transaction-rollback codes — **`40001`**
(`serialization_failure`) and **`40P01`** (`deadlock_detected`) — now map to it.
They previously mapped to `UnexpectedServerError`, which carries the same two
`Text` fields. **No other constructor changed**, and no other SQLSTATE moved:
`UnexpectedServerError` still receives every server error outside the recognised
set.

The old mapping was actively misleading. `UnexpectedServerError` documents
itself as "*not* generally retryable — investigate", while these two codes are
exactly the ones PostgreSQL expects a client to retry: the transaction rolled
back completely and nothing was committed. `TransientTransactionFailure`
documents the retry contract, including that the store already retried the
append once before surfacing it.

This is a change of *classification only*. No lock ordering, SQL, or hot-path
code changed, so append and read throughput are unaffected.

### What to do

1. **Find every exhaustive match over `StoreError`.** Search for the type name
   and for its distinctive constructors — `WrongExpectedVersion`,
   `StreamAlreadyExists`, `PoolAcquisitionTimeout`, `ConnectionLost`,
   `HistoryRetentionActive`, `DuplicateEvent`, `EventAlreadyLinked`,
   `LinkSourceEventMissing`, `UnexpectedServerError`. A `case` or `\case` that
   lists constructors without a `_` fallback needs a new arm.

2. **Classify it as retryable / transient.** In a function that answers "should
   the caller retry this?", `TransientTransactionFailure` belongs with
   `ConnectionLost` and `PoolAcquisitionTimeout`, not with
   `UnexpectedServerError`. If the surrounding code distinguishes an
   *optimistic-concurrency conflict* (which needs the aggregate re-hydrated and
   the decision recomputed) from a *transient infrastructure failure* (which
   only needs the same work attempted again), this is the second kind.

3. **Find any match on the literal SQLSTATE strings.** A pattern like
   `UnexpectedServerError "40001" _` or `UnexpectedServerError "40P01" _`, or a
   guard comparing the code field against those literals, is now **dead code**
   — the value it was written to catch no longer takes that shape. Move it to
   the new constructor. Grep for `40001` and `40P01` across the whole
   repository, including tests and any error-to-HTTP or error-to-metric
   mapping table.

4. **Leave every other `UnexpectedServerError` site alone.** Do not take this
   edge as licence to reclassify the constructor generally; only those two
   codes moved out of it.

### What not to do

- Do not add a `_ ->` fallback to an exhaustive match to silence the warning.
  The exhaustiveness is deliberate: it is what forces this review on the next
  release too.
- Do not change retry *limits*, backoff, or lock ordering. This edge changes
  which error value carries which condition, nothing else.

### Proving it

Build the project and run whatever suite covers error handling. If the project
builds with `-Wall`, a remaining non-exhaustive match will show as
`[-Wincomplete-patterns]`; treat a clean build as necessary but not sufficient,
because the SQLSTATE-literal sites in step 3 produce no warning at all.

## Part B — Kiroku migration `0010` has a new checksum

### What changed

`kiroku-store-migrations` 0.3.2.0 and 0.3.2.1 shipped a payload of migration
`0010` whose `history_retention_leases.lease_id` default named `uuidv7()`
**unqualified**. `uuidv7()` is a PostgreSQL 18 builtin; on PostgreSQL 17 the
name came from a fallback that Kiroku's `0001` installs into the Kiroku schema,
reachable only through the `search_path` that `0001` itself sets. So `0010`
parsed on a fresh install — where `0001` had just run in the same session — and
failed with **SQLSTATE 42883** on every ordinary upgrade of a database already
bootstrapped through `0009`. That is the PostgreSQL 17 upgrade path, and 0.4.0.0
is the release that fixes it.

0.4.0.0 corrects the payload. Editing a released payload is normally forbidden,
and a forward migration is the documented remedy; there is none available here,
because the withdrawn payload fails at DDL *parse* time, so no migration ordered
after it can ever run.

`pg-migrate` keys an applied migration by `(component, migration)` and verifies
the exact SHA-256 of its payload bytes. Correcting the payload therefore changes
`0010`'s checksum, and a database that already applied the withdrawn payload
fails every subsequent `up` and `verify` with **`MigrationChecksumMismatch`**
until its ledger row is re-baselined.

0.4.0.0 also adds forward migration `0011`, which converges an already-`0010`
database: it publishes `kiroku.uuidv7()` where missing and rebinds `lease_id`'s
stored default to it. It is a no-op on a database that applied the corrected
`0010`.

### Which databases are affected

| Database | Needs the re-baseline |
|---|---|
| Applied `0010` under 0.3.2.x — **every PostgreSQL 18 database**, and a fresh PostgreSQL 17 install performed by 0.3.2.x | **Yes**, once, before the next `up` |
| Never reached `0010` — every ordinary PostgreSQL 17 upgrade, the path this release fixes | No. `0010` is still pending there and applies from the corrected payload |
| Ephemeral, template, or per-suite test databases | No. They apply the whole plan from scratch |

### What to do

1. **Establish whether this project has a persistent database at all.** Read
   the project's configuration, compose files, migration tooling, and CI. A
   project whose only databases are created per test run needs nothing here —
   say so.

2. **If it does, determine whether that database applied `0010` under 0.3.2.x.**
   This is a *read-only* question, answerable against a replica, a restored
   clone, or with a `SELECT` against the ledger. The withdrawn payload's
   checksum is

   ```
   257d94b8ea24156af0ee477196c5a6682cf5616cf8dfd0cfc527a49b5e7a97ac
   ```

   and the corrected payload's is

   ```
   debc19187d79cd263be66c6c85cd789c1176e508d562a27390095aaa70f650c4
   ```

   The ledger lives in `pgmigrate.migrations` unless the application configured
   a different schema through `ledgerConfig` — check the project's migration
   runner before assuming the default. A row for component `kiroku`, migration
   `0010`, carrying the withdrawn checksum, is the affected case.

   If you cannot reach any database, do not guess. Report the query the
   operator should run and what each answer means.

3. **Name the fixup; do not run it.** The re-baseline script ships in the
   `kiroku-store-migrations` source distribution as
   `ledger-fixups/2026-08-16-rebaseline-0010-checksum.sql`. It rewrites that one
   checksum, touches no schema, and is idempotent — its `UPDATE` matches only a
   row still carrying the withdrawn value, so a second run, or a run against a
   database that applied the corrected payload, matches nothing. It is wrapped
   in a transaction. If the ledger uses a non-default schema, the script's
   `to_regclass` call must be edited to match.

   The operator sequence is: run the fixup once → `verify` → `up` (which applies
   `0011` and converges the schema).

4. **Route a data-bearing database to a rehearsal.** For anything holding real
   data, the correct path is backup → restore a clone → apply the fixup and the
   following `up` on the clone → verify → then production. If this project has a
   skill, runbook, or documented procedure for cohort database cutovers, name it
   and hand off to it. Do not perform the cutover inside this edge.

5. **Update the project's own migration expectations.** Kiroku's plan grows from
   ten migrations to eleven. If this project's tests assert a migration count, a
   list of pending migration ids, an offset into a composed plan (`drop N`), or
   the Kiroku schema comment — which becomes
   `Managed by pg-migrate component kiroku through 0011` — those fixtures need
   updating. This part *is* source work: make the edits and run the suite.

### What not to do

- **Do not run the fixup, or any `UPDATE` against a migration ledger, on a
  database you have not established is disposable.** Rewriting a ledger row is
  how a database silently skips a migration.
- Do not hand-write the re-baseline SQL. Use the script that ships with the
  package, so the checksums come from the release rather than from this prompt.
- Do not attempt to "repair" a `MigrationChecksumMismatch` by deleting the
  ledger row, by re-running `0010`, or by disabling verification.
