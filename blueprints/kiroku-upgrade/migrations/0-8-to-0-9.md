# kiroku-store 0.8.0.2 → 0.9.0.0

This edge covers two packages, released together:

- **`kiroku-store-migrations` 0.6.0.0** — new forward migration `0012`, which
  copies each stream's category onto its `$all` junction rows, adds a check
  constraint that requires it, and builds the index category reads now use.
- **`kiroku-store` 0.9.0.0** — the append statements write that column, and
  category reads (plain and consumer-group) scan that index. The public Haskell
  API is unchanged.

The two must move **together, in one ordered step**. Neither package works
with the other side's old version:

| Running code | Schema | Result |
|---|---|---|
| `kiroku-store` 0.9 | before `0012` | every append fails with SQLSTATE **`42703`** (undefined column) |
| `kiroku-store` 0.8.x or older | after `0012` | every append fails with SQLSTATE **`23514`** (check violation) |

There is **no rolling-deploy path**. The upgrade is: stop every process that
appends with the old library, apply `0012`, then start the new code. Reads by
old code keep working against the new schema; only appends break.

This edge has a database half (Part B), which is where most of the work is, and
a small source half (Part A). Each has its own precondition.

## Precondition

Report this edge **not applicable** only when *both* halves are inapplicable:
the project's source, tests, benchmarks, and fixtures contain no SQL that
inserts into `stream_events` and no assertion about Kiroku's migration count or
schema comment, **and** the project has no PostgreSQL database that has applied
Kiroku migrations and holds data that must survive.

A project that reaches this edge through another library's blueprint (Keiro,
Kioku, a Shibuya adapter) and never names Kiroku in its own source usually has
no Part A work, but if it runs that library's composed migration plan against a
persistent database, Part B applies in full.

If exactly one half applies, do that half and say so in your summary. That is a
completed edge, not a partial one.

## Part A — source that writes junction rows or counts migrations

### What changed

`kiroku.stream_events` gains a nullable `category TEXT` column. On `$all` rows
(`stream_id = 0`) it holds the source stream's category — the text before the
first `-` of the stream name, the same value as the generated
`kiroku.streams.category`. Source-stream rows and link rows leave it `NULL`.
The constraint `ck_stream_events_all_category`
(`CHECK (stream_id <> 0 OR category IS NOT NULL)`) rejects an `$all` row
without it.

Code that appends through `kiroku-store` needs no change. Code that writes
junction rows **directly** — test fixtures, benchmark seeders, data importers,
pgbench scripts — now fails with `23514` on every `$all` row it inserts.

Kiroku's migration plan also grows from eleven migrations to twelve, and the
schema comment becomes `Managed by pg-migrate component kiroku through 0012`.

### What to do

1. **Find direct junction-row writers.** Search the whole repository, including
   tests, benchmarks, scripts, and `.sql` files, for `INSERT INTO stream_events`
   and `INSERT INTO kiroku.stream_events`. A multi-line insert may put the table
   name on its own line, so also search for `stream_events` near `INSERT`.

2. **Set `category` on every `$all` row they write.** For each insert whose
   `stream_id` is `0`, add `category` to the column list and supply the source
   stream's category:
   - Inside a CTE that inserts or updates the stream row, add `category` to its
     `RETURNING` list and select it, which is what Kiroku's own append
     statements do.
   - With the stream id in hand, `(SELECT category FROM kiroku.streams WHERE stream_id = …)`.
   - In PL/pgSQL with the stream name in a variable,
     `split_part(v_stream_name, '-', 1)`.

   Leave inserts for source-stream rows and link rows alone; `NULL` is correct
   there.

3. **Update the project's migration expectations.** If tests assert Kiroku's
   migration count, a list of pending migration ids, an offset into a composed
   plan (`drop N`), or the Kiroku schema comment, update them for `0012`.

4. **Move the dependency bounds** if the project names Kiroku packages:
   `kiroku-store ^>=0.9` and `kiroku-store-migrations ^>=0.6`.

### Proving it

Build, then run every suite that migrates a database and writes to it. An
insert you missed fails at run time with `23514`, not at compile time, so a
clean build proves nothing here. If a suite needs a database you do not have,
say which commands you did not run.

## Part B — migration `0012` on a database that holds data

### What changed

`0012` runs as **one transaction**:

1. adds the column;
2. **rewrites every `$all` row** to fill it from `kiroku.streams`, with the
   `no_update_stream_events` immutability trigger disabled for that one
   statement and re-enabled before commit;
3. validates the check constraint, reading the table once;
4. builds `ix_stream_events_all_by_category`, reading the `$all` rows again.

Its duration grows with the number of events in the store, and **appends block
until it commits**. A failure at any point rolls everything back, including the
trigger state, and leaves the database on `0011`. Afterwards the rewritten rows
leave dead tuples behind, which `VACUUM (ANALYZE) kiroku.stream_events`
reclaims; it also refreshes planner statistics for the new index.

### Which databases are affected

| Database | What it needs |
|---|---|
| Persistent, holds data, has applied Kiroku migrations through `0011` | The ordered cutover below, in a maintenance window |
| Already on `0012` | Nothing |
| Ephemeral, template, or per-suite test databases | Nothing. They apply the whole plan from scratch |
| A local, disposable development database the project's tooling recreates | Nothing beyond the ordinary migrate |

### What to do

1. **Establish whether this project has a persistent database at all.** Read
   the project's configuration, compose files, migration tooling, deployment
   manifests, and CI. A project whose only databases are created per test run
   needs nothing here — say so.

2. **If it does, size it from read-only evidence.** Against a replica, a
   restored clone, or with plain `SELECT`s:

   ```sql
   -- Has 0012 already applied?
   SELECT to_regclass('kiroku.ix_stream_events_all_by_category') IS NOT NULL;

   -- The global head: an upper bound on the $all rows 0012 rewrites.
   SELECT stream_version FROM kiroku.streams WHERE stream_id = 0;

   -- The on-disk size of the table it rewrites.
   SELECT pg_size_pretty(pg_total_relation_size('kiroku.stream_events'));
   ```

   If the Kiroku schema has another name in this project, substitute it. If you
   cannot reach any database, do not guess: report these queries and what each
   answer means.

3. **List every process that appends with the old library.** These are the
   processes that must be stopped before `0012` and started again only on
   `kiroku-store` 0.9: application services, background workers, command-line
   tools (including `kiroku-cli` builds on 0.8), import jobs, and anything built
   on a framework that still resolves `kiroku-store` 0.8. Processes that only
   read, subscribe, or serve metrics may keep running on the old library during
   the window; their reads work on either schema.

4. **Hand the operator the cutover sequence; do not run it.**

   1. Rehearse on a restored clone of production: apply `0012` there and time
      it. That time, not an estimate, sizes the maintenance window.
   2. Stop every appending process from step 3.
   3. Run `verify`, then `up` (with `kiroku-store-migrate`, or the project's own
      composed runner, which puts Kiroku's plan first).
   4. Run `VACUUM (ANALYZE) kiroku.stream_events;`.
   5. Deploy and start the processes on `kiroku-store` 0.9.

   If this project has a skill, runbook, or documented procedure for database
   cutovers, name it and hand off to it.

5. **Check the deploy order in the project's own automation.** If CI/CD or a
   container entrypoint runs migrations as part of starting a new version, then
   during a rolling deploy the old instances still running will fail every
   append with `23514` as soon as the first new instance migrates. Report this,
   and say that the deployment must stop old writers before the migration runs,
   for example with a recreate strategy, a scale-to-zero step, or a separate
   migration job gated on the old version being down.

### What not to do

- **Do not apply `0012` to a database you have not established is
  disposable.** It blocks appends for as long as it runs, and that length is
  only known from a rehearsal.
- Do not hand-write the column, backfill, constraint, or index. They ship in
  `kiroku-store-migrations`; run its migration.
- Do not drop or `NOT VALID` the check constraint to let old writers keep
  running. Their `$all` rows would carry no category, and category reads and
  category subscriptions on 0.9 would silently never see those events.
- Do not re-enable a rolling deploy by keeping 0.8 writers alive "just for the
  window". Every append they attempt after `0012` fails.
